## R01｜预算错误仍在测试预期中

## R02｜购置税公式错误，高价边界会少算税

**复核指出**：原公式 `min(应纳÷2, 1.5万)`，把结果当成**实缴额**。正确是 `减税额 = min(原税额×50%, 1.5万)`，`实缴 = 原税额 − 减税额`。财政部示例：不含税 50 万元 → 实缴 3.5 万元；按原公式会算成 1.5 万元。

**成因**：把"减税额上限"读成了"应缴上限"。政策原文（财政部 税务总局 工信部公告 2023 年第 10 号）限制的是**减掉多少**，不是**缴多少**。

**修正**：

1. `facts.py` 重写 `compute_tax()`，明确返回四个量：`base`（计税价）、`original`（原税额）、`reduction`（减税额）、`due`（实缴）。公式为 `due = original − min(original×50%, 15000)`。
2. 增加独立期望表 `TAX_EXPECTED`，用**不经过本程序算法**的三个已知点校验：
   - 含税 565,000 → 原税 50,000／减税 15,000／实缴 **35,000**（财政部示例，不含税 50 万）
   - 含税 339,000 → 30,000／15,000／**15,000**（正好触顶）
   - 含税 125,800 → 11,132.74／5,566.37／**5,566.37**（未触顶）
   三者任一不符即 `check` 失败。
3. 文档层同步改口径：`purchase-cost.md` 第 2 节、`SKILL.md` 第四步第 4 条、`README.md`、`expert-body.md` 一律改成"减税额上限 1.5 万元（上限作用在减掉多少，不是缴多少）"。
4. `test-cases.md` 硬阻断项增加一条：**把减税额上限当成实缴上限**即阻断。

**说明一处自我纠错**：我第一版把期望表写成 `(500000, …)`，把 50 万当成含税价，校验直接报 `实得 44247.79`。改成 565,000（含税）才对上财政部的 3.5 万。这条记在这里，因为"用独立期望校验算法"的价值就在这里——它抓到了我自己写错的期望值。

## R03｜JSON 不是数值的唯一来源，检查器会漏报

**复核指出**：注入 7 类错误后检查器全部返回 PASS；配置矩阵里的数字实际来自 Python 常量，不是真的从 JSON 读的。

**成因**：`render()` 用的是 `facts.py` 里的 `TRIMS` 常量，`check()` 只做价格的正则比对。JSON 名义上是唯一来源，实际上是第二来源。

**修正**：

1. **删除 `facts.py` 里全部产品数据**（`TRIMS` 等），只保留算法、Schema 与校验规则。JSON 成为唯一可编辑数据源。
2. `check()` 改为读 JSON → 校验 → 重新渲染 → 与磁盘上的视图比对；**视图缺失或过期一律判失败，不再 SKIP**。
3. 校验项扩展到：顶层与逐行 `checked` 日期格式、主键 `(market,year,trim,field)` 唯一、字段名在已定义集合内、单位正确、`status`／`evidence` 枚举合法、价格可解析为数值、`unknown` 必须写"未确认"、`conflict` 必须写"未决"、来源 ID 不得悬空、`need_evidence` 必须有来源、有来源必须有证据、**scope 越界**（通过 `source_covers` 与 `covers.unsupported` 判）、证据等级不得超过来源的 `evidence_max`、必需字段齐全、各版本字段集合一致（`wltc_pure_range` 列为可选）。
4. 新增 `selftest`：在临时副本上注入错误场景，要求基线退出 0、每个注入场景各自非 0、合法修改并重新渲染后回到 0。（v0.5.0 当时为 **7 个错误场景 + 1 个基线 + 1 个合法更新 = 9 行**；v0.5.1 扩为 **18 + 1 + 1 = 20 行**。）

**验证**：
```
$ python scripts/facts.py check

视图：trim-comparison.md / purchase-cost.md 税表 均为最新
RESULT: PASS

$ python scripts/facts.py selftest
baseline                     exit=0 期望0  OK
price_changed_to_1           exit=1 期望非0  OK
invalid_source_id            exit=1 期望非0  OK
L1_without_source            exit=1 期望非0  OK
missing_checked_date         exit=1 期望非0  OK
invalid_status               exit=1 期望非0  OK
missing_matrix               exit=1 期望非0  OK
duplicate_primary_key        exit=1 期望非0  OK
legal_update_after_render    exit=0 期望0  OK
SELFTEST: PASS
```

**注意能力边界**：`selftest` 证明的是"这些注入场景拦得住"，不是"所有错误都拦得住"。例如"两个来源给了不同数值但都合法"这种语义冲突，程序判不了，仍靠人工与 `conflicts` 记录。v0.5.1 又补了 11 个场景（负座位、非数值电池、非法日期、年款越界、来源 ID 重复、冲突主张清空、无关来源抬等级、过宽 `covers`、预算输入被改、预算期望被改），但"语义冲突"仍然只能靠人。

## R04｜逐字段来源有空引用与版本越界

**复核指出**：16 条记录引用不存在的来源 ID `yiche-c16-config-2027`；C16 纯电电池容量、部分 C11 参数引用了"明确没读到该版本字段"的来源。

**成因**：来源 ID 是手写的，改来源清单时漏改；来源条目只有一句 `supports` 描述，没有机器可校验的适用范围。

**修正**：

1. **删除 `yiche-c16-config-2027` 这个不存在的 ID**，16 条记录重新映射到真实来源（C16 纯电电池容量改为 `weixin-c16-guide`，`status=media`）。审计输出：`悬空引用: 0`、`yiche-c16 残留: 0`。
2. 每条来源新增两项机器可校验字段：
   - `covers: {trims, fields, unsupported[]}`——声明能支持哪些版本、哪些字段，`unsupported` 列出"登记了但没读到"的版本／字段，支持通配；
   - `evidence_max`——这份来源最好能达到的证据等级。
3. `validate()` 据 `source_covers()` 做 glob 匹配，**引用越界直接报错**。已修掉的典型越界：
   - `autohome-c11-config-2027` 的 `unsupported` 补上 `c11-300-*` 全部字段与 `c11-640-zx` 全部字段（该页未读到增程版与 640 智享版）；
   - `autohome-c16-config-2027` 的 `unsupported` 补上 `c16-630-*` 的 `slow_charge`／`battery_capacity`，以及 `c16-*` 的 `wheelbase`；
   - `yiche-c11-config-2027` 标 `evidence_max=indirect`，引用它的记录证据等级不得超过 indirect。
4. **拆分 `status` 与 `evidence`**：`confirmed` 说的是"这个值有多确定"，`evidence` 说的是"支撑材料是直读、部分读到还是间接"。上一版把"首页间接证据"写成 `confirmed/direct`，本轮降级。当前仍是 `confirmed + indirect` 的有 **43 条**（C11 全部参数、C16 轴距），合计 `direct 39／partial 126／indirect 96`。

**未完全解决**：这 43 条的事实值有交叉来源，但证据等级确实只到 indirect。**不把"值可用"当成"等级够"，也不为了好看把等级调高。**

## R05｜"高配已知具备"仍被写成"确认增加"

**复核指出**：低配芯片未知时，不能把高配的 8650 写成"多花的钱买到了什么"。必须区分"高配已知具备"与"两版已证实差异"。

**成因**：把"高配参数表里有 A"直接推成"低配没有 A"，这在低配参数缺失时是无效推断。

**修正**：`trim-deltas.md` 重写，第 0 节确立核心规则：

> **只知道高配有 A，不能证明低配没有 A。**

并把每个差价项拆成两栏 + 一列来源等级：

| 列 | 含义 |
|---|---|
| 高配已知具备 | 高配资料里有没有这个配置（是／未读到） |
| 两版差异 | 已证实／媒体所述／未证实／争议 |
| 来源等级 | 官方／配置库／媒体 |

落到具体结论：

- **C10 §1**：8650、激光雷达、28 个感知硬件——"高配已知具备=是"，但"两版差异=**未证实**"（智享版芯片与感知数量在已读资料里没有逐项值）；AR-HUD 三处说法不一致，列**争议**，不作加价理由。
- **C11 §2**：明确写"**没有一行可以标'已证实'**"，上一版"确认增量"表述作废。
- **Q16 的示例答案**改成："能确定的是激光雷达版有这套硬件；不能确定的是智享版没有。"
- `answer-patterns.md` 规则四、`SKILL.md` 第四步第 2 条、`buyer-intake.md` 硬规则同步改。
- 客户端清单 F3／F5 的判据从"列确认增量"改为"两栏分开写"，并把"把高配已知具备写成两版已证实差异"列入失败项。
