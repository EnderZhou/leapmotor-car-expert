## 2. 先修复的阻断问题

### R01｜预算错误仍在测试预期中

位置：`test-cases.md` Q17、Q22；`tests/offline-regression-v0.4.0.md` 对应通过记录。

- **Q17**：14 万裸车预算的合格候选写了 C10 四款，其中 14.28 万已超预算 2,800 元。按当前指导价，只有 12.58、13.28、13.58 万三款满足裸车价格上限；这只是价格筛选，还须核对补能、座位等条件。
- **Q22**：16 万落地预算下，把 15.28 万的纯电五座写成可谈，却直接排除更便宜的 14.88 万六座。按表内税率，前者车价加税约 159,561 元，仅剩约 439 元；后者约 155,384 元，剩约 4,616 元。保险等未报价时，两者都不能被无条件确认；应展示剩余费用额度并逐项核验，不能凭空给“约 15.9 / 16.2 万”的结论。
- **Q18 / Q20 / Q21**：问题只说预算，预期却没有一致要求先区分裸车与落地。Q19 也应在两种口径下分别筛选，不能只排除最贵一款。
- “14 万落地对应裸车 12.6–12.9 万”“12.58 万车型落地 13.5 万上下”缺少统一的费用假设。应列算式和输入，或只算“可用于其他费用的余额”。缺少费用报价，不能产生保证结论。

修复原则：采用已确认且适用的成交报价；没有报价时才以指导价作演示。不得假设优惠一定可得，也不能在用户提供有效书面报价后仍机械地以指导价将其排除。价格、税费、座位等确定性约束用程序判定，不能只靠模型自检。

### R02｜购置税公式错误，高价边界会少算税

位置：`source/leapmotor-car-expert/references/purchase-cost.md:29`。

现文把“实缴税额”写成 `min(应纳税额 ÷ 2, 1.5 万元)`。这算出的是减税额，并非实缴税额。

对 2026—2027 年符合减税条件的新能源乘用车，应写为：

```text
原应纳税额 = 发票不含增值税计税价格 × 10%
减税额 = min(原应纳税额 × 50%, 15,000 元)
实缴税额 = 原应纳税额 − 减税额
```

按含增值税车价折算时，须明确 13% 增值税率等适用假设；实际优先读取发票不含税价格。不能把指导价估算当最终税务核定。

财政部的例子：不含增值税车价 50 万元，原税额 5 万、减税额 1.5 万，实缴 **3.5 万元**。现公式会误算成 1.5 万元。本库价位未触及上限，所以现有 15 行税表恰好没有暴露错误。依据：[财政部政策解读](https://m.mof.gov.cn/zcjd/202306/t20230627_3892750.htm)、[上海税务 2026 年答复](https://shanghai.chinatax.gov.cn/bsfw/nszx/hdfk/202602/t479413.html)。

发票日期和适用目录必须核验；不能由“新能源”或“2027 款”直接推导税收资格。README 的“每辆上限 1.5 万”也应统一写成“每辆乘用车减税额上限 1.5 万元”。

另：交付摘要声称 `facts.py check` 会校验税额表，本次检查代码未发现此项能力。应实现后再写已通过。

### R03｜JSON 尚不是数值的唯一来源，检查器会漏报

位置：`scripts/facts.py` 的 `build`、`render`、`check`。

`build()` 从 Python 的 `TRIMS` 生成 JSON；`render()` 仍从同一份 Python 常量生成数值，只从 JSON 读取记录数、未知数等汇总。JSON 声明应先改 JSON，矩阵却要求先改 Python。修改 JSON 数值后，矩阵可以保持旧值且检查继续通过。

本次在临时副本中执行，不修改仓库原始数据：

| 临时注入的问题 | 当前结果 | 应有结果 |
|---|---|---|
| 只把 JSON 第一条价格改成 1，保持矩阵不动 | PASS | 不同步 FAIL；合法变更后重新生成才可通过 |
| 已确认事实改引不存在的来源 ID | PASS | FAIL |
| L1 价格清空来源 | PASS | FAIL |
| 删除核对日期 | PASS | FAIL |
| 状态改成未定义的字符串 | PASS | FAIL |
| 删除矩阵文件 | PASS，打印 SKIP | 必需产物缺失 FAIL |
| 重复一条相同版本、相同字段的记录，再生成矩阵 | PASS | 重复主键 FAIL |

修复要求：

1. 确定一份可编辑事实数据；推荐 JSON。删除 Python 中与之并行维护的产品数值，生成器只负责读取、校验、格式化。
2. 主键至少覆盖市场、年款、版本、字段；校验重复、必填属性、数据类型、单位、状态枚举、来源 ID 存在性及日期格式。
3. 所有非未知的事实和价格级别均须有合适证据。来源为间接、转载或复核失败时，在机器数据和展示中一致披露，不能只在正文页脚提醒。
4. 关键字段缺失、必要视图缺失和陈旧均返回非零退出码。`render` 也应先验证数据，不能成功发布非法数据视图。
5. 差价、税费示例及汇总数字应派生生成或被自动核对；不要仅把配置矩阵自动化，就宣称所有重复数字已消除。

### R05｜“高配已知具备”仍被写成“确认增加”

位置：`references/trim-deltas.md` 第 1、2 节；客户端 F3。

C10 的 8650、28 个感知硬件仍列为“确认增量”，但同页承认官方未逐版本限定、智享版芯片和感知数量未知。**只知道高配有 A，不能证明低配没有 A，因而不能确认加钱增加了 A。**

应拆成“高配已知配置 / 已证实的两版差异 / 媒体所述差异 / 未知差异”。C11 表中标“确认增量”的依据来自媒体、配置库，也与表头“确认增量仅指官方证据”的定义冲突。建议将“是否证实差异”和“来源等级”分为两列，避免互相替代。不得仅凭版本名称不含某配置就认定没有该配置。

## 6. 实施顺序与验收
